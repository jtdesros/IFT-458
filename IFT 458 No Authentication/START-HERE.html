IFT 458 Assignment 1

Database authentication without authorization

Complete this assignment independently using the included Level 1 Game Score Tracker API. You will connect it to your own database, create users and scores, demonstrate unprotected game changes, and submit screenshots and a log. A successful login checks a password but creates no lasting authenticated session. That is the behavior you are investigating.

Read this guide in order. Save evidence as you work. This release replaces the older Word handout and does not require an Atlas setup script from another project. The Canvas assignment supplies the due date.

3 Configure the application

Copy config.env.example to .env in the project root. Use your editor's copy and rename commands, or one of the following:

Windows PowerShell:

Copy-Item config.env.example .env

macOS or Linux:

cp config.env.example .env

Do not name it .env.txt. Edit the copy, retaining the other defaults:

NODE_ENV=development
PORT=4001
API_VERSION=/api/v1
STUDENT_NAME="Your Full Name"
STUDENT_ID="Your ten-digit ASU ID"
BCRYPT_ROUNDS=12
DATABASE=mongodb+srv://ift_user:<password>@YOUR_CLUSTER.mongodb.net/ift458_level1?retryWrites=true&w=majority
DATABASE_PASSWORD="YOUR_URI_ENCODED_DATABASE_PASSWORD"

Replace ift_user with your database username and YOUR_CLUSTER.mongodb.net with the exact hostname copied from Atlas. Keep the literal <password> placeholder in DATABASE; put the database user's password in DATABASE_PASSWORD. Encode special characters in the username and password for a URI before using them here (for example, @ becomes %40, # becomes %23, and % becomes %25). Encode once, not twice. Do not use an online password encoder. Retain any additional connection options from Atlas.

Only .env is needed. The app also supports config.env for compatibility, but .env wins when both define a setting. Environment variables already set in your terminal take precedence over both files. Save changes and restart the app for them to take effect.

5 Understand the data and the learning outcomes

The User model validates name, email, and password confirmation and hashes a new password before saving. Normal user queries omit the password field, and signup/login responses do not expose it. Game requires title, developer, and description; submittedBy is unverified text. Score requires gameTitle, integer points from 0 through 100000000, and a valid-looking playerEmail. Allowed statuses are submitted, verified, rejected, and disputed. The email is supplied by the caller and is not proof of identity. userId normally remains null for API-created Level 1 scores.

You may read any source file. Edit your configuration files only for these tasks. If your instructor separately assigns a coding task, make the requested changes only in controllers/ and include a screenshot of them. Do not change the schemas, routes, middleware, logging, tests, or server files for this assignment.

Using Swagger for Level 1

OpenAPI describes this API's paths, inputs, and responses. Swagger UI displays that description and lets you send real requests. In this project, SwaggerTFT458.js supplies the description and /api-docs displays it. You can read the file, but do not edit it for this assignment.

Start the configured application with npm start. Open http://localhost:4001/api-docs and use the local server. The /api/v1 prefix is already part of the server URL; do not add it again to an ID field.

  1. Expand Users, Games, or Scores and choose an operation.
  2. Read the required fields and expected responses.
  3. Choose Try it out. Replace the example JSON with your own values. Use double quotes and no trailing commas.
  4. For {id}, paste the actual _id returned by a matching create or list request. Do not paste braces, the whole response, or a game's ID into a score request.
  5. Choose Execute once. Read the actual Server response, including its code and body. Inspect the request URL if it failed.
  6. Capture the request and actual response for your evidence. Avoid revealing real database passwords in any screenshot.
Operation Normal successful result
POST /users/signup 201; user details, no password
POST /users/login 200; credential check, no session cookie or token
GET /games and GET /scores 200; results count and records
POST /games and POST /scores 201; new record and _id
GET /games/{id} and GET /scores/{id} 200; one record
PATCH /games/{id} and PATCH /scores/{id} 200; updated record
DELETE /games/{id} and DELETE /scores/{id} 204; empty body

A 400 indicates rejected input, 401 indicates an unsuccessful login, 404 indicates a missing route or record, and 409 indicates an existing signup email. Read the returned message and the matching request in the log. A 500 needs investigation in the terminal and log.

There is no authorization step or token to paste for Level 1. The absence of access checks is intentional. A caller can change submittedBy, claim someone else's playerEmail, or set a score's status to verified. The server does not establish that caller's identity for these actions.

Score input uses gameTitle, points, and playerEmail. Score status values are submitted, verified, rejected, and disputed. Book, loan, or borrowing fields do not belong to this API.

For the exact request bodies, task order, and evidence requirements, follow ASSIGNMENT.md. Read the Schemas section in Swagger alongside models/ to understand validation. Calling an operation sends a real request and can change your assignment database.
